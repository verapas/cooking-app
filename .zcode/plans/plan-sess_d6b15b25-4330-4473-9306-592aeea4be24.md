# Plan: SQLite → MariaDB + `[deploy]`-Trigger + Container-Reparatur

## 1. Datenbank-Wechsel (SQLite → MariaDB)

### 1.1 Abhängigkeiten (`package.json`)
- **Entfernen:** `better-sqlite3` (dependencies), `@types/better-sqlite3` (devDependencies)
- **Hinzufügen:** `mysql2` (dependencies), `node-flywaydb` (dependencies) — letzteres führt Flyway-Migrationen als Node-API aus, ideal für "beim Booten migrieren".
- `pnpm-workspace.yaml`: `allowBuilds`-Block komplett entfernen (ungültiger Platzhalter); `onlyBuiltDependencies: ["better-sqlite3", "canvas"]` → `["canvas"]` (better-sqlite3 fliegt raus). `canvas` bleibt, weil es devDep ist.
- `engines` und `packageManager` neu setzen: `"node": ">=22"`, `"packageManager": "pnpm@11.17.0"`.

### 1.2 `src/lib/server/db.ts` — kompletter Rewrite
- Statt `new Database(path)`-Singleton: **`mysql2.createPool`** mit Env-Variablen `DB_HOST`, `DB_PORT` (default 3306), `DB_USER`, `DB_PASSWORD`, `DB_NAME` (Defaults für lokales Dev). Pool wird als Singleton exportiert.
- Alle PRAGMAs entfallen (`journal_mode`, `foreign_keys`).
- Die bedingten `ALTER TABLE`-Migrations entfallen vollständig — Flyway übernimmt das Schema. **`db.ts` enthält kein DDL mehr** (außer ggf. `SET FOREIGN_KEY_CHECKS` für Seed-Resets, was aber bei `seedIfEmpty` nicht nötig ist).
- Der `recipes_updated_at`-Trigger wird in `V1__init.sql` als MariaDB-Trigger angelegt (mit `NOW()`), nicht mehr in `db.ts`.
- **Result-API-Umstellung** der 7 Auth-Helper: `info.lastInsertRowid` → `result.insertId`, `res.changes > 0` → `result.affectedRows > 0`. Alle Helper werden `async`.
- Zentrale Row-Mapper: `mysql2` gibt für `DATETIME` ein `Date`-Objekt und für `TINYINT(1)` echtes Boolean zurück. Die Mapper serialisieren `created_at`/`updated_at` zu ISO-Strings (damit TS-Typen unverändert `string` bleiben) — sonst brechen die Client-Komponenten. Für `is_favorite` reicht `Boolean(r.is_favorite)` (funktioniert mit echtem Boolean genauso).

### 1.3 `src/lib/server/queries.ts` — async-Migration (~330 Zeilen)
- **Alle** Funktionen werden `async`: `listCategories`, `getCategoryBySlug`, `createCategory`, `updateCategory`, `deleteCategory`, `listRecipes`, `searchRecipes`, `listFavorites`, `toggleFavorite`, `countRecipes`, `getMainRecipeId`, `listRecipeVersions`, `getRecipeWithVersion`, `getEffectiveImageUrl`, `getRecipe`, `createRecipe`, `updateRecipe`, `deleteRecipe`, plus interne Helper `resolveCategoryId`/`insertChildren`.
- API-Muster `db.prepare(sql).all/get/run(params)` → `await pool.query(sql, [params])` mit Destructuring `const [rows] = await pool.query(...)`.
- `db.transaction(() => {...})` → `const conn = await pool.getConnection(); await conn.beginTransaction(); try { ...; await conn.commit(); } catch { await conn.rollback(); } finally { conn.release(); }` für `createRecipe` und `updateRecipe`.
- SQLite-Upsert (`ON CONFLICT(slug) DO UPDATE SET ... excluded.*`) → `INSERT ... ON DUPLICATE KEY UPDATE name=VALUES(name), icon=VALUES(icon), sort_order=VALUES(sort_order)`.
- `"order"` (reserviert) konsequent mit Backticks quoten.
- TS-Typen (`Category`, `RecipeListItem[]` etc.) bleiben identisch — Row-Mapper in `db.ts` stellen die Kompatibilität her.

### 1.4 `src/lib/server/seed.ts` — an Flyway vorbeiführen
- `seedUser()` bleibt erhalten (bcrypt + `getUserByUsername`/`createUser`) — wird weiterhin im Hook beim Start gerufen, weil Admin-Credentials aus Env-Variablen kommen und nicht ins Schema gehören.
- `seedIfEmpty()` bleibt erhalten, nutzt aber async-Queries (`countRecipes`, `createRecipe`).
- Direkter `getDb()`-Lookup für Bolognese-Parent → `getRecipeByTitle`-Helper (neu, async) oder `listRecipes`-Filter.

### 1.5 `src/lib/server/session.ts`
- Bleibt als Wrapper erhalten, wird `async`. (Aktuell ungenutzt — `hooks.server.ts` importiert `validateSession` direkt. Behalten für对称ische API.)

### 1.6 `src/hooks.server.ts` — Migration einhängen
- **Neu:** Beim ersten Request (im `initialized`-Block) `await runMigrations()` aufrufen, **bevor** `seedUser()`/`seedIfEmpty()`. `runMigrations` ist ein neuer Helper in `db.ts` (oder `src/lib/server/migrate.ts`), der `node-flywaydb` mit der in `db/migration/` liegenden SQL-Datei und der Pool-Config aufruft.
- Reihenfolge: migrate → seedUser → seedIfEmpty. Bei Migrations-Fehler: App-Start scheitern lassen (klarer Log, kein stiller Betrieb).

### 1.7 API-Routen mit direktem DB-Zugriff (4 Dateien)
- `api/auth/login/+server.ts`, `api/auth/logout/+server.ts`, `api/auth/verify/+server.ts`: Aufrufe von `getUserByUsername`/`createSession`/`deleteSession`/`validateSession` um `await` ergänzen (Functions werden ja async).
- `api/recipes/[id]/image/+server.ts`: Zwei rohe SQL-Statements (`SELECT id, image_url FROM recipes ...` und `UPDATE recipes SET image_url = ? ...`) werden entweder über einen neuen Helper in `queries.ts` (`getRecipeImageUrl(id)`, `setRecipeImageUrl(id, url)`) abgewickelt oder direkt über `pool.query` mit `await`. Empfehlung: Helper in `queries.ts`, um die rohe-SQL-Inskonsistenz zu beenden.

### 1.8 `+page.server.ts`-Dateien (7 Load-Funktionen)
- Alle Load-Funktionen sind bereits `async` (SvelteKit-Pattern) — nur die `await`-Aufrufe an die Query-Funktionen ergänzen. Keine Logikänderung.

### 1.9 Flyway-Migrationsskripte (`db/migration/`)
- **`V1__init_schema.sql`** — alle 6 Tabellen als MariaDB-DDL: `INTEGER ... AUTO_INCREMENT`, `DATETIME DEFAULT CURRENT_TIMESTAMP`, `TINYINT(1) NOT NULL DEFAULT 0` für `is_favorite`, Backticks für `"order"`, Foreign Keys nativ (kein PRAGMA), Indices, Trigger `recipes_updated_at` mit `NOW()`. Direkt aus dem bestehenden Schema übersetzt.
- **`V2__seed_admin.sql`** — optionaler Platzhalter; in der Praxis wird der Admin aber über `seedUser()` aus Env-Vars beim Start angelegt. Entfällt vermutlich — klären bei Implementierung.
- Demo-Rezepte (`seedIfEmpty`) bewusst **nicht** als Migration — sie sind seeding, nicht migration, und sollen nur laufen wenn die DB leer ist.
- **Wichtig:** Flyway braucht eine `flyway_history`-Tabelle (legt es selbst an). Der DB-User braucht DDL-Rechte (`CREATE`, `ALTER`, `INDEX`, `TRIGGER`) — dokumentiere das in `deploy/.env.example` und `CLAUDE.md`.

## 2. Pipeline: `[deploy]`-Trigger

### 2.1 `docker-publish.yml` — Trigger-Logik umbauen
- Trigger bleibt: `push` auf `main`, `workflow_dispatch`. (Tags `v*.*.*` optional, falls du das noch willst — Task erwähnt es ursprünglich, dein Fokus liegt jetzt aber auf `[deploy]`.)
- **Neuer Gate im `publish`-Job:** `if: contains(github.event.head_commit.message, '[deploy]')`. Das steuert, dass der Build+Push nur bei `[deploy]` in der Commit-Message läuft.
- `metadata-action@v5` bekommt `with: images: ghcr.io/${{ github.repository }}` (Lowercase-Variante via `github.repository` — GitHub-Repo-Namen sind case-insensitive, GHCR erwartet lowercase).
- Tag-Strategie via `tags`-Input der metadata-action: `type=edge,branch=main` → `:edge`; `type=sha,prefix=,format=short` → `:sha-<short>`. Kein `:latest` mehr bei main-Merge (nur via Git-Tag, falls gewünscht — als auskommentierte Variante).
- `id: meta` nur einmal deklarieren (Duplikat entfernen).
- **`deploy`-Job wirklich auskommentieren** (kompletter Job-Block als `#`-Kommentar) mit Hinweis „Aktivieren, wenn Build stabil läuft", plus Hinweis, dass der Tower-Workflow auf dem Server das Deployment ohnehin übernimmt — der SSH-Deploy-Job ist nur ein Fallback.
- `permissions: { contents: read, packages: write }` beibehalten.

### 2.2 `ci.yml` — läuft weiterhin bei jedem PR/Push
- YAML-Einrückung bei `on:` reparieren (`branches: [main]` korrekt unter `pull_request:` bzw. `push:` einrücken).
- `setup-node@v4` mit `cache: 'pnpm'` statt manuellem `actions/cache`-Step.
- Steps bleiben: install → `pnpm check` → `pnpm build` (Build-Step war bisher nur im Dockerfile, jetzt auch in CI als schnelles Feedback). **Keine** DB-Abhängigkeit — Typecheck läuft ohne laufende DB, weil `mysql2`-Typen statisch sind.
- Läuft **unabhängig** von `[deploy]` (für jeden PR/Push, als Quality-Gate).

## 3. Container-/Compose-Reparatur

### 3.1 `Dockerfile` — korrekter Multi-Stage-Build
- `FROM node:22-bookworm-slim AS base` — nur `corepack enable`, `WORKDIR /app`, kein vorzeitiger `pnpm install` (zieht volle Deps in jede Stage, ist falsch).
- `build`-Stage: `package.json` + `pnpm-lock.yaml` kopieren → `pnpm install --frozen-lockfile` → Source + `tsconfig.json` + `svelte.config.js` + `vite.config.js` + `static` + `src` + `db/migration` kopieren → `pnpm check && pnpm build`. **`db/migration/` MUSS ins Image**, damit Flyway beim Booten läuft.
- `prod-deps`-Stage: nur `package.json` + `pnpm-lock.yaml` → `pnpm install --prod --frozen-lockfile`. Default-Target von pnpm ist `./node_modules`, nicht `/root/.npm` — korrekter Pfad im COPY.
- `final`-Stage: `COPY --from=prod-deps /app/node_modules ./node_modules`; `COPY --from=build /app/build ./build`; `package.json` kopieren; `db/migration` explizit kopieren, weil es im `build/`-Output nicht automatisch landet.
- **ENV-Variablen neu:** `PORT=3000`, `IMAGES_DIR=/data/images`, `BODY_SIZE_LIMIT=25M`. **`DATABASE_PATH` ENTFÄLLT.** Neue Defaults: `DB_HOST=mariadb`, `DB_PORT=3306`, `DB_NAME=cooking`, `DB_USER=cooking` — Passwort und endgültiger Host NICHT ins Image (kommen zur Laufzeit).
- `USER node` aktivieren, `VOLUME ["/data"]`, `EXPOSE 3000`, `CMD ["node", "build"]`.
- HEALTHCHECK-Bug beheben: `node -e "fetch('http://localhost:3000/login').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"`. `/login` liefert ohne Session 200 (ist in `publicPaths`).
- BuildKit-Cache-Mounts: `--mount=type=cache,id=pnpm,target=/pnpm/store` mit `ENV PNPM_HOME=/pnpm` — ohne externe `from=`-Images.
- Kommentare auf Deutsch für nicht-offensichtliche Zeilen.
