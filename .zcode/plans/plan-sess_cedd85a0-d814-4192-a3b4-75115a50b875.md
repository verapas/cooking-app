# Plan: KI-Chat für Rezepterstellung & -verbesserung (OpenRouter, Streaming)

## Ziel
- **Nav-Eintrag „Neues Rezept"** → öffnet eine **frische Chat-Session** (nicht persistiert). Man plant ein Rezept mit der KI, am Ende wird es per `POST /api/recipes` angelegt.
- **Button auf der Rezept-Detailseite** → öffnet den Chat **mit dem bestehenden Rezept als Kontext**. Beim Speichern frei wählbar: **Original überschreiben** (`PUT`) oder **als neue Version** (`POST` + `parent_recipe_id`).
- **OpenRouter** als Provider (damit auch `z.ai GLM`-Modelle nutzbar), **Streaming-Antworten**.
- **API-Key & Modell konfigurierbar in der App** (Settings-Seite, in DB gespeichert).

## Wichtige Erkenntnis: hoher Wiederverwendungsgrad
- `RecipeInput` (`{ title, category_slug, steps[], ingredients[] mit step_order }`) ist **exakt** die Form, die die KI liefern soll → `createRecipe()` / `updateRecipe()` machen den Rest. **Keine Schema-Änderung an Rezepten nötig.**
- Versionierung existiert bereits: neue Version = `POST` mit `parent_recipe_id` + `version_name`.
- Auth für `POST /api/chat` kommt **gratis** über `hooks.server.ts`.

## Konzept: zweistufige KI-Interaktion (robust + modellunabhängig)
1. **Chat-Phase (streaming):** normale Konversation mit der KI (Rezept planen, Fragen, Vorschläge). Antworten werden per SSE an den Client gestreamt. Der Nachrichtenverlauf lebt **nur im Client-State** (Svelte 5 Runes) — beim Verlassen der Seite weg, nicht persistiert.
2. **Abschluss-Phase (strukturiert):** User klickt **„Rezept erstellen"** → ein einzelner, nicht-streamender Aufruf mit `response_format: { type: 'json_object' }` + strengem Schema-Prompt (aus dem bisherigen Verlauf). Server validiert das JSON gegen `RecipeInput` und gibt es zurück.
3. **Vorschau & Speichern:** UI zeigt das fertige Rezept als Vorschau. Beim Speichern geht es über die **bestehenden REST-Endpunkte** — kein neues Speicher-Handling.

## Neue Abhängigkeit
- `openai` (npm) — OpenRouter ist OpenAI-kompatibel (nur `baseURL` umstellen auf `https://openrouter.ai/api/v1`). Das SDK nimmt uns Streaming-Parsing und Tool-/JSON-Handling sauber ab.

## Details pro Komponente

### 1. Settings (DB + Helpers + API + Seite)
**`db/migration/V2__settings.sql`** (Flyway, neue Datei — V1 wird nicht angerührt):
```sql
CREATE TABLE IF NOT EXISTS settings (
  `key`   VARCHAR(64) PRIMARY KEY,
  `value` TEXT NOT NULL,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```
**`src/lib/server/settings.ts`** — async Helpers im Stil von `queries.ts`.
**`GET /api/settings`** gibt `{ openrouter_model, has_key: boolean, key_hint: '••••' + last4 }` — **der Key geht nie im Klartext an den Client.** `PUT /api/settings` nimmt `{ openrouter_api_key?, openrouter_model? }` (Key nur schreiben, wenn gesendet).

### 2. AI-Modul (`src/lib/server/ai.ts`)
- Liest Key/Modell zur Laufzeit aus `settings` (nicht aus env) — damit in der App wechselbar.
- `streamChat(messages, systemPrompt)` → async-Generator von Text-Deltas; baut `openai`-Request an OpenRouter mit `stream: true`.
- `finalizeRecipe(messages, contextRecipe?)` → einzelner Aufruf mit `response_format: json_object`, liefert geparstes `RecipeInput`. Prompt enthält die `IngredientInput`/`StepInput`-Schema-Vorgaben + die Kategorien-Liste (für `category_slug`).
- Zwei System-Prompts: „neues Rezept planen" und „bestehendes Rezept verbessern" (mit Rezept-Daten im Prompt).

### 3. Chat-Endpunkte
- **`POST /api/chat`** — Body `{ messages: [{role, content}], mode: 'new'|'improve', recipeId?: number }`. Wählt System-Prompt nach Modus, gibt `Response` mit `text/event-stream` zurück (ReadableStream schreibt `data: {delta}`/`data: [DONE]`). Auto-geschützt.
- **`POST /api/chat/finalize`** — gleicher Body, ruft `finalizeRecipe()`, validiert, gibt `{ recipe: RecipeInput }` zurück. Auto-geschützt.

### 4. Chat-UI (`/chat`, Modus via Query)
- **`/chat`** → Modus `new` (leerer Chat, Speichern = `POST /api/recipes`).
- **`/chat?recipe=<id>`** → Modus `improve`; `+page.server.ts` lädt das Rezept + Kategorien, gibt sie an die Seite. Speichern-Buttons: „Überschreiben" (`PUT /api/recipes/[id]`) und „Als neue Version" (`POST` + `parent_recipe_id = getMainRecipeId`, `version_name` abfragbar).
- `ChatPanel.svelte`: Nachrichtenliste (`$state`-Array), Eingabe + Senden, liest SSE via `res.body.getReader()` + `TextDecoder`, hängt Deltas an die laufende Antwort. Button „Rezept erstellen" → `/api/chat/finalize` → **Vorschau-Karte** (Titel, Zutaten, Schritte) → Speichern über bestehende REST-API (gleiche `fetch`-Muster wie `edit/+page.svelte`). Verlauf nur im Speicher.

### 5. Navigation & Icon
- `icons.ts`: `sparkles: '<path .../>',` ergänzen.
- `NavDrawer.svelte`: zwischen „Suche" (line ~60) und dem Divider „Neues Rezept" (`/chat`) einfügen (ggf. `{#if auth.isLoggedIn}`); „Einstellungen" (`/settings`) bei den Admin-Links unten.

### 6. Routing & Auth
- `POST /api/chat*` und `PUT/POST /api/settings` sind durch `hooks.server.ts` **automatisch session-geschützt** (keine Hook-Änderung).
- `/chat` und `/settings` als Seiten sind standardmäßig protected (nicht in `publicPaths`) → nur für eingeloggten Admin. **Keine Hook-Änderung nötig.**

2. **AI-Modul + Chat-API (Streaming + Finalize)** — serverseitig testbar (curl/fetch).

5. **Polish & Doku** (`CLAUDE.md`/`README`), Edge-Cases (leerer Key, Modell-Fehler, JSON-Reparatur).

## Aufwandsschätzung
ca. **2–3 Tage** (≈14–20 h): Settings ~3–4 h, AI-Modul ~3–4 h, Chat-Endpunkte ~1–2 h, Chat-UI ~4–6 h, Detail-Button/Routing ~1 h, Doku/Polish ~1–2 h. Keine Schema-Migration an Rezepten, keine Änderung an `createRecipe`/`updateRecipe`.

## Offen / Hinweise
- **Modell-Default:** ich trage ein plausibles Default-Modell in die Settings ein (z. B. `z-ai/glm-4.6`), exakter OpenRouter-String ist frei editierbar.
- **Finalize-Robustheit:** `response_format: json_object` + serverseitige Validierung + eine Reparatur-Logik (Retry ohne Stream, falls JSON kaputt). Breit kompatibel auch mit GLM.
- Der API-Key wird **niemals** an den Client gesendet (nur `has_key` + maskierter Hint).
